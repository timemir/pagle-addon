# Core: Recovery

> Status: Done · Source: [Catch log hardening #302](https://github.com/timemir/pagle-backend/issues/302) · ADR: [0017](../../adr/0017-recovery-preserves-the-original-branch.md)

Recovery restores server-held Accepted history into the active Catch log while preserving the complete original local branch. The backend owns prefix selection, salvage replay, conflict retention, and competitive approval. The addon owns the final local snapshot guard and early application. The exact cross-language wire format is [Recovery v1](../../contracts/recovery-v1.md).

## Rules

- **RCV-R1** `/pagle recovery export` presents every numbered part of the complete authoritative local snapshot. The Player copies every part and pastes them together on the Catch log's Recovery page. This is separate from a multipart Upload and contains the full indexed character metadata, exact records, test flag, and nullable `selfFound`. Nil and false remain distinct. Nothing changes in `PagleLog` while exporting.
- **RCV-R2** The downloaded package contains only the fixed `Pagle_Recovery` TOC, data assignment, and instructions. The data addon is load-on-demand with no dependency on Pagle. Core explicitly loads it before ordinary SavedVariables opening, character registration, build or skill recording, and projection binding. A newly installed folder requires returning to character selection to be discovered. An existing folder can consume updated data at reload. Ordinary fishing requires no additional reloads.
- **RCV-R3** Core validates backend origin using the shipped key ring and distinct Recovery signature domain, parses strict data, verifies the application ID and every digest, and confirms the target log. It recomputes the complete live local snapshot immediately before any mutation. A mismatch or invalid package leaves the entire local log unchanged, reports why, and blocks normal initialization. The Player can remove `Pagle_Recovery` or export a new snapshot. Decoded payloads are never executed as Lua.
- **RCV-R4** A valid application builds its replacement separately. Without yielding between publication steps, it preserves a deep copy of the whole original `PagleLog`, including unknown fields, stores staged source sequence numbers and explanations, publishes the restored log, and records a stable application marker. Restoration assigns exact raw bytes rather than using normal Append, which would regenerate ties or other state. Every accepted identity, mapping, time, and tie remains exact.
- **RCV-R5** The completion marker is bound to the application ID, result digest, and target log, and is checked before the expected-old-snapshot guard. A persistent package cannot reapply after normal login or subsequent fishing. An interrupted application leaves either the original branch or the complete replacement recoverable. Applying the same plan again creates no duplicate records or archive.
- **RCV-R6** Core discards all derived caches affected by restoration and changes the Recovery generation. Every Core and Module projection rebuilds, including a Module enabled later. Settings and unrelated Player choices survive. Normal rebuild celebration rules prevent restored records from firing fresh reward announcements. A previous projection position or matching record count cannot suppress rebuilding.
- **RCV-R7** Only the backend's fully replay-validated salvage is installed, using its original identities. Exact duplicates collapse. Conflicting records, incompatible older observations, and actions requiring review remain in the preserved original branch with stable reason codes. Purchases, rerolls, and Prestiges are never repaired by changing amounts, ranks, snapshots, or IDs. Derived progress may change after replay.
- **RCV-R8** `/pagle recovery inspect [application ID]` shows preserved staged records and their reasons. Without an ID it inspects the latest application. `/pagle recovery archives` lists archived application IDs. These records remain available for inspection and are not silently appended to the restored log.
- **RCV-R9** After application, the Player uploads normally and confirms consistency through the website or Companion. A client claim alone cannot resolve an Integrity conflict. Backend admission and current validation must establish the planned result. Newer or unrelated conflicts and deleted evidence remain protected.
- **RCV-R10** The Player controls the addon and local files. A signature proves package origin, not Catch authenticity. A plausible first-submission forgery remains possible. Mac Players use manual snapshot export, website planning, and the downloaded package without a Mac Companion.

## Data

`PagleRecovery` holds the complete original branch archive keyed by application ID, staged original sequence numbers and reasons, expected and resulting snapshot digests, server checkpoint and rules, and completed application markers. It is account-wide and separate from derived projection state. `PagleLog` remains the active restored source. The complete original branch includes unknown local fields even though the semantic snapshot hashes only the defined authoritative fields.

## Bounds

Recovery v1 accepts at most 100 indexed characters, 100,000 entries, and 128 MiB of decoded snapshot data. Manual numbered Base64 fragments contain at most 65,536 characters each. The package contract defines canonical netstrings, counts, nullable values, exact framing, and strict trailing-data rejection. These bounds are separate from normal Upload page and pushed-content caps.
